# BRC-100 Wallet Interface Contract

BRC-100 defines the **standard wallet-to-application interface** for BSV. It is vendor-neutral, unchanging, and specifies exactly what a compliant wallet must do — not how it does it.

This document summarises the contract for reference when building `bsv-wallet`. The groupings, ordering, and descriptions below mirror the "Interface Structure" section of BRC-100.

## Interface Structure

The interface comprises 28 methods grouped into six functional areas. Each method has a numeric call code (used in the binary ABI over Wallet Wire).

### Transaction Operations

| Code | Method |
|------|--------|
| 1 | `createAction` |
| 2 | `signAction` |
| 3 | `abortAction` |
| 4 | `listActions` |
| 5 | `internalizeAction` |
| 6 | `listOutputs` |
| 7 | `relinquishOutput` |

- **Creation**: `createAction` creates a new Action — a Bitcoin transaction augmented with descriptive metadata and optional categorisation (labels). It can either fully construct and sign a transaction or return a `signableTransaction` reference if some inputs must be signed or processed later. The method always requires at least one input or one output; otherwise it must return an error. If `inputs` are provided, `inputBEEF` is required to supply context and validation data. The two are complementary: `inputs` define the UTXOs being consumed, `inputBEEF` provides the transaction inclusion proofs needed for validation. Both must not conflict. Every input requires an `inputDescription`. If `basket` is not provided for an output, that output is considered untracked — it will not appear in `listOutputs` and the wallet maintains no metadata about it.
- **Signing**: `signAction` allows signing and processing previously created transactions from `createAction`.
- **Aborting**: `abortAction` facilitates cancellation of transactions that have not yet been completed.
- **Internalisation**: `internalizeAction` enables wallets to accept and manage incoming transactions by parsing, tagging, and organising outputs.
- **Listing**: `listActions` and `listOutputs` allow querying transactions and outputs based on specific criteria like labels, baskets, and tags. They are purely organisational tools and cannot be used as triggers or conditional hooks for other wallet operations. They serve only for later searching and categorising actions.
- **Relinquishment**: `relinquishOutput` releases an output from a basket tracked by the wallet, even if it has yet to be spent.
- **Pre-built transactions**: If you already have a fully constructed transaction in BEEF format and simply need to internalise it into the wallet, `internalizeAction` is the appropriate method. `createAction` is meant for constructing new transactions within the wallet, not for adding an existing transaction.
- **Tags vs labels**: Transaction-level labels categorise entire transactions (Actions) and are used with `listActions`. Output-level tags categorise individual outputs and are used with `listOutputs`. Both are organisational metadata fields and do not trigger special wallet logic or external processes. They exist solely for searching, filtering, and organising data.

### Public Key Management

| Code | Method |
|------|--------|
| 8 | `getPublicKey` |
| 9 | `revealCounterpartyKeyLinkage` |
| 10 | `revealSpecificKeyLinkage` |

- **Key retrieval**: `getPublicKey` facilitates the retrieval of public keys, be they derived keys based on protocols or the user's main identity keys.
- **Key linkage**: `revealCounterpartyKeyLinkage` and `revealSpecificKeyLinkage` disclose key relationships, as specified in BRC-69, with additional support for future zero-knowledge proof schemes outlined in BRC-97. These are essential for identity verification and the auditing of interactions between parties.

### Cryptography Operations

| Code | Method |
|------|--------|
| 11 | `encrypt` |
| 12 | `decrypt` |
| 13 | `createHmac` |
| 14 | `verifyHmac` |
| 15 | `createSignature` |
| 16 | `verifySignature` |

- **Encryption/decryption**: `encrypt` and `decrypt` implement secure encryption and decryption of data using derived keys and consistent protocol definitions, enabling private exchanges of information between counterparties.
- **HMAC operations**: `createHmac` and `verifyHmac` allow creation and verification of Hash-based Message Authentication Codes to ensure data integrity.
- **Signatures**: `createSignature` and `verifySignature` enable creation and verification of digital signatures, both public and private, essential for validating the authenticity of transactions, documents, and data.

### Identity and Certificate Management

| Code | Method |
|------|--------|
| 17 | `acquireCertificate` |
| 18 | `listCertificates` |
| 19 | `proveCertificate` |
| 20 | `relinquishCertificate` |
| 21 | `discoverByIdentityKey` |
| 22 | `discoverByAttributes` |

- **Certificate acquisition**: `acquireCertificate` allows the wallet to obtain identity certificates, either by directly saving them or through a standardised issuance protocol. Conversely, `relinquishCertificate` allows an old certificate to be removed.
- **Certificate listing and discovery**: `listCertificates`, `discoverByIdentityKey`, and `discoverByAttributes` enable querying of identity certificates owned by the user or others based on identity keys or specific attributes.
- **Proving identity certificates**: `proveCertificate` leverages selective revelation protocols defined in BRC-52 while integrating future-proof proof schemes from BRC-97. This provides enhanced flexibility and enables users to securely prove their identity or certified attributes to third parties when required.

### Blockchain and Network Data

| Code | Method |
|------|--------|
| 25 | `getHeight` |
| 26 | `getHeaderForHeight` |
| 27 | `getNetwork` |
| 28 | `getVersion` |

- **Blockchain height**: `getHeight` retrieves the current height of the blockchain.
- **Block header retrieval**: `getHeaderForHeight` retrieves the block header at a specific height.
- **Network and version information**: `getNetwork` and `getVersion` retrieve information about the network (mainnet or testnet) and the wallet's version.

> **Note**: The BRC-100 Interface Structure narrative refers to `getMerkleRootForHeight` in this group, but the formal TypeScript interface and call codes table both define `getHeaderForHeight` at code 26. The TypeScript interface is the binding contract.

### Authentication

| Code | Method |
|------|--------|
| 23 | `isAuthenticated` |
| 24 | `waitForAuthentication` |

- **User authentication**: `isAuthenticated` checks the user's authentication status, ensuring they've set up their wallet before operations are attempted.
- **Authentication wait**: `waitForAuthentication` waits for the user to complete authentication and returns once the wallet has been fully set up.

## Data Types and Constraints

BRC-100 defines constrained data types to ensure consistency:

- **Booleans**: `BooleanDefaultFalse`, `BooleanDefaultTrue` — defaults if not provided.
- **Integers**: `Byte` (0-255), `PositiveIntegerOrZero` (0 to 2^32-1), `SatoshiValue` (1 to 2.1 x 10^15), `PositiveIntegerDefault10Max10000`.
- **Strings**: `HexString`, `Base64String`, `ISOTimestampString`, plus specialised strings for descriptions (5-50 chars), labels (<300 chars), basket names (<300 chars), tags (<300 chars), version strings (7-30 chars), certificate field names (<50 chars).

## What the Contract Does NOT Specify

Everything below is implementation detail left to the wallet vendor:

| Concern | BRC-100 says... |
|---------|-----------------|
| **Storage** | Nothing. How actions, outputs, and certificates are persisted is unspecified |
| **Broadcasting** | Nothing. How transactions reach the network is unspecified |
| **UTXO pool / pre-funding** | Nothing. Auto-funding, change management, and pool replenishment are internal |
| **Sync / replication** | Nothing. Multi-storage sync (e.g. `sync_states`) is an implementation concern |
| **Key storage** | Nothing. How the master private key is held and protected is unspecified |
| **Permission UX** | Conceptually described (BRC-43 security levels) but no methods for managing grants |
| **Fee estimation** | Nothing. How the wallet calculates fees is unspecified |
| **Coin selection** | Nothing. Which UTXOs are chosen as inputs is unspecified |

## Foundational BRCs

BRC-100 builds on and mandates compliance with these specifications:

| BRC | Domain | Role |
|-----|--------|------|
| BRC-2 | Wallet | Encryption/decryption (AES-256-GCM) |
| BRC-3 | Wallet | Digital signature creation/verification |
| BRC-29 | Payments | Payment internalisation (P2PKH derivation) |
| BRC-42 | Key derivation | BKDS — the key derivation scheme (ECDH + secp256k1) |
| BRC-43 | Key derivation | Security levels, protocol IDs, key IDs, counterparties |
| BRC-44 | Key derivation | Reserved admin protocols (prefix `admin`) |
| BRC-45 | Tokens | UTXOs as tokens |
| BRC-46 | Wallet | Output baskets for UTXO tracking |
| BRC-52 | Peer-to-peer | Identity certificates with selective revelation |
| BRC-62 | Transactions | BEEF format |
| BRC-67 | Transactions | SPV verification |
| BRC-69 | Key derivation | Key linkage revelations (auditability) |
| BRC-72 | Key derivation | Protecting linkage information in transit |

## Implications for bsv-wallet

`BSV::Wallet::Client` is the concrete implementation of a BRC-100 wallet. It includes `BSV::Wallet::BRC100::Interface`, which is composed of the six sub-modules above:

- `BSV::Wallet::BRC100::Transaction`
- `BSV::Wallet::BRC100::KeyManagement`
- `BSV::Wallet::BRC100::Crypto`
- `BSV::Wallet::BRC100::Identity`
- `BSV::Wallet::BRC100::Authentication`
- `BSV::Wallet::BRC100::Network`

Everything else — `StorageAdapter`, `BroadcastQueue`, `UTXOPool`, `ReplenishmentWorker`, `CoinSelector`, `FeeEstimator`, `ChangeGenerator` — is internal machinery that exists to *fulfil* the contract, not part of the contract itself. These live under `lib/bsv/wallet/` alongside `client.rb`.

The contract (`BRC100::Interface`) is the public API surface. The implementation (`Client`) is the private detail.
